# Turno - 1 de Setembro de 2026

## Contexto inicial

Continuação da limpeza de software não utilizado no WIN11HS-CLIENT (agent 001) e início da configuração de automação de resposta a incidentes (Active Response) no Wazuh manager (servidor helderlab-server, agent 002).

## Limpeza de software

Identificados via análise de MUICache (histórico de execuções) programas instalados mas nunca executados: QEMU, Oracle VirtualBox, MySQL Workbench, XAMPP, Redis on Windows, Zotero, Raspberry Pi Imager. Decisão: manter WampServer (mais atual, melhor postura de segurança) e remover XAMPP (builds Windows sem atualização desde 2023).

Desinstalador nativo do XAMPP falhou a meio da execução. Remoção manual da pasta bloqueada por um processo `cmd.exe` esquecido com o diretório como working directory — identificado com precisão usando **Handle** (Sysinternals/Microsoft) em vez de tentativa-erro. Mesma ferramenta reutilizada depois para o OBS Studio, que tinha um driver de câmara virtual (`obs-virtualcam-module64.dll`) a bloquear a remoção da pasta de instalação.

## Achado de segurança: injeção de comando no Wazuh manager

Ao configurar Active Response (bloqueio automático de IPs em força bruta SSH, regra 5763), a validação da configuração revelou um **bloco `<localfile>` malicioso** já presente no `ossec.conf` do manager, disfarçado de log:

<command>echo "..." wazuh-logcollector: INFO: [PoC-RCE-844F9BFB] $(echo aWQ= | base64 -d | sh)" >> /var/ossec/logs/ossec.log</command>
<frequency>10</frequency>


O comando (decodificado: `id`) corria a cada 10 segundos com os privilégios do container do manager, comprovando execução de código arbitrário — mecanismo de prova de conceito de RCE, com potencial para ser substituído por qualquer payload.

### Investigação

- Confirmado que o ficheiro-fonte do host (versionado no repositório do projeto) estava limpo — a injeção só existia no volume Docker em execução, descartando acesso direto ao filesystem ou ao Git.
- Descartado agente Wazuh falso (só 3 agentes reconhecidos: manager, WIN11HS-CLIENT, helderlab-server).
- Descartados logins SSH externos suspeitos (único IP externo aceite era o próprio IP público da rede, confirmado por `curl ifconfig.me`).
- Identificado vetor mais provável: API REST do Wazuh (porta 55000) com credenciais de fábrica ainda ativas — as mesmas usadas como exemplo público num advisory de segurança conhecido (CVE-2025-24016, já corrigida na versão instalada, mas as credenciais de fábrica continuavam válidas e documentadas publicamente).

### Remediação

1. Bloco malicioso removido do `ossec.conf` via edição controlada (validação XML em cada passo com `xmllint`).
2. Manager reiniciado e confirmado arranque completo e saudável (todos os módulos, sem repetição do comando malicioso em ciclos subsequentes do log).
3. Rotação de credenciais: senha do utilizador `admin` do Wazuh Indexer alterada via geração de hash bcrypt (`hash.sh`) e aplicação ao cluster com `securityadmin.sh`, com atualização correspondente das variáveis de ambiente no `docker-compose.yml` e recriação dos containers afetados.
4. Confirmado login funcional com as novas credenciais.

## Lição do dia

Um exercício de configuração de rotina (Active Response) expôs um incidente de segurança real e já existente na própria infraestrutura de monitorização — o SIEM que deveria detetar ataques tinha sido ele próprio alvo de uma prova de conceito de execução remota de código. Credenciais de fábrica documentadas publicamente são um vetor de ataque tão real quanto qualquer CVE, independentemente de o software em si estar atualizado e corrigido. A validação de configuração em cada passo (XML, logs, testes de login) foi essencial para reparar o serviço sem introduzir novos erros durante a remediação.
