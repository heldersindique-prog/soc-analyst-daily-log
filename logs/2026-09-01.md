# Turno - 1 de Setembro de 2026

## Contexto inicial

Continuação da limpeza de software não utilizado no WIN11HS-CLIENT (agent 001) e início da configuração de automação de resposta a incidentes (Active Response) no Wazuh manager (servidor helderlab-server, agent 002).

## Limpeza de software

Identificados via análise de MUICache (histórico de execuções) programas instalados mas nunca executados: QEMU, Oracle VirtualBox, MySQL Workbench, XAMPP, Redis on Windows, Zotero, Raspberry Pi Imager. Decisão: manter WampServer (mais atual, melhor postura de segurança) e remover XAMPP (builds Windows sem atualização desde 2023).

Desinstalador nativo do XAMPP falhou a meio da execução. Remoção manual da pasta bloqueada por um processo `cmd.exe` esquecido com o diretório como working directory — identificado com precisão usando **Handle** (Sysinternals/Microsoft) em vez de tentativa-erro. Mesma ferramenta reutilizada depois para o OBS Studio, que tinha um driver de câmara virtual (`obs-virtualcam-module64.dll`) a bloquear a remoção da pasta de instalação.

## Achado de segurança: injeção de comando no Wazuh manager

Ao configurar Active Response (bloqueio automático de IPs em força bruta SSH, regra 5763), a validação da configuração revelou um **bloco `<localfile>` malicioso** já presente no `ossec.conf` do manager, disfarçado de log:

<command>echo "..." wazuh-logcollector: INFO: [PoC-RCE-844F9BFB] $(echo aWQ= | base64 -d | sh)" >> /var/ossec/logs/ossec.log</command>
<frequency>10</frequency>


O comando (decodificado: `id`) corria a cada 10 segundos com os privilégios do container do manager, comprovando execução de código arbitrário — mecanismo de prova de conceito de RCE, com potencial para ser substituído por qualquer payload.

### Investigação

- Confirmado que o ficheiro-fonte do host (versionado no repositório do projeto) estava limpo — a injeção só existia no volume Docker em execução, descartando acesso direto ao filesystem ou ao Git.
- Descartado agente Wazuh falso (só 3 agentes reconhecidos: manager, WIN11HS-CLIENT, helderlab-server).
- Descartados logins SSH externos suspeitos (único IP externo aceite era o próprio IP público da rede, confirmado por `curl ifconfig.me`).
- Identificado vetor mais provável: API REST do Wazuh (porta 55000) com credenciais de fábrica ainda ativas — as mesmas usadas como exemplo público num advisory de segurança conhecido (CVE-2025-24016, já corrigida na versão instalada, mas as credenciais de fábrica continuavam válidas e documentadas publicamente).

### Remediação

1. Bloco malicioso removido do `ossec.conf` via edição controlada (validação XML em cada passo com `xmllint`).
2. Manager reiniciado e confirmado arranque completo e saudável (todos os módulos, sem repetição do comando malicioso em ciclos subsequentes do log).
3. Rotação de credenciais: senha do utilizador `admin` do Wazuh Indexer alterada via geração de hash bcrypt (`hash.sh`) e aplicação ao cluster com `securityadmin.sh`, com atualização correspondente das variáveis de ambiente no `docker-compose.yml` e recriação dos containers afetados.
4. Confirmado login funcional com as novas credenciais.

## Lição do dia

Um exercício de configuração de rotina (Active Response) expôs um incidente de segurança real e já existente na própria infraestrutura de monitorização — o SIEM que deveria detetar ataques tinha sido ele próprio alvo de uma prova de conceito de execução remota de código. Credenciais de fábrica documentadas publicamente são um vetor de ataque tão real quanto qualquer CVE, independentemente de o software em si estar atualizado e corrigido. A validação de configuração em cada passo (XML, logs, testes de login) foi essencial para reparar o serviço sem introduzir novos erros durante a remediação.

## Continuação do turno: remediação de vulnerabilidades no helderlab-server

Após resolução do incidente de segurança, retomado o foco original: 388 vulnerabilidades críticas no helderlab-server (agent 002), maioritariamente ligadas a kernels Linux desatualizados.

### Diagnóstico

- Kernel ativo (`uname -r`) confirmado como `7.0.0-28-generic` — desatualizado, mas com `7.0.0-30-generic` já instalado e pronto (apenas pendente reinício).
- Confirmado que `docker restart: always` garante recuperação automática do Wazuh manager após reboot do host.

### Remediação

1. Aplicadas 8 atualizações de segurança pendentes (bibliotecas de sistema, sem exigir reinício).
2. Reiniciado o servidor para arrancar com o kernel `7.0.0-30-generic`.
3. Removido o kernel antigo (`7.0.0-28-generic`) via `apt purge`, seguido de `update-grub`.
4. Resultado: 388 → 209 vulnerabilidades críticas (179 eliminadas, correspondentes exatamente ao kernel removido).
5. Identificado que o CVE com maior contagem (CVE-2024-35366, ffmpeg) tinha patch disponível apenas via **Ubuntu Pro / ESM Apps** — confirmado pelo aviso já presente no MOTD do SSH.
6. Ativado Ubuntu Pro (token pessoal gratuito, até 5 máquinas), habilitando ESM Apps, ESM Infra e Livepatch.
7. Aplicadas as atualizações ESM disponíveis (ffmpeg e bibliotecas `libav*`, entre outras — incluindo o próprio Caddy, o proxy reverso exposto publicamente).
8. Resultado: 209 → 179 vulnerabilidades críticas.

### Estado final e decisão

As 179 vulnerabilidades restantes referem-se todas ao kernel `7.0.0-30-generic`, confirmado como a versão mais recente disponível nos repositórios (`apt-cache policy` mostra candidato = instalado). Este é um padrão documentado e reconhecido publicamente pela própria equipa do Wazuh (múltiplas issues no GitHub oficial) em que o detetor de vulnerabilidades compara números de versão do kernel de forma que gera falsos positivos em sistemas Ubuntu já corrigidos, por divergência entre o versionamento upstream do kernel e o versionamento de backport da Canonical.

Sem mais ação corretiva disponível no momento (kernel já na versão mais recente, ESM Apps já ativo), decisão de analista: aceitar como risco residual documentado, sem continuar a investigar individualmente cada CVE sem retorno prático — mantendo isto sinalizado para revisão no próximo ciclo de atualizações do kernel.

**Progresso total do turno**: 388 → 179 vulnerabilidades críticas (54% de redução), com causa raiz identificada e ação corretiva aplicada em cada categoria.

# Turno - 3 de Setembro de 2026

## SOAR - Active Response no Wazuh

Implementação e teste do Active Response (componente SOAR) no Wazuh manager.

### Configuração

Dois blocos de `<active-response>` configurados no `ossec.conf`, ligados ao script `firewall-drop`:

- **Regra 5763** (SSH brute force, 8+ falhas de utilizador válido): bloqueio de 180 segundos
- **Regra 5710** (tentativa com utilizador inválido, 1 evento basta): bloqueio de 3600 segundos (1 hora)

Decisão de design: utilizadores inválidos têm tolerância zero - nenhum utilizador legítimo tenta entrar com um nome que não existe. Utilizadores válidos têm margem de 8 tentativas antes do bloqueio, cobrindo erros humanos normais.

### Teste e validação

Simulada tentativa de força bruta SSH a partir do WIN11HS-CLIENT (192.168.1.121) contra o helderlab-server, usando um utilizador inexistente (`utilizadorfalso`).

Resultado confirmado no log `/var/ossec/logs/active-responses.log`:
- Regra 5710 disparada
- IP 192.168.1.121 bloqueado automaticamente via `firewall-drop`
- Técnicas MITRE ATT&CK identificadas automaticamente: T1110.001 (Password Guessing) e T1021.004 (SSH)
- Bloqueio confirmado pelo `Connection timed out` na tentativa seguinte do mesmo IP

### Persistência da configuração

Configuração salva em dois locais para sobreviver a recriações do container:
- Volume Docker (em execução): `/var/ossec/etc/ossec.conf`
- Ficheiro-fonte do host (persistente): `wazuh_manager.conf` no repositório `wazuh-siem`

Versionado no GitHub: https://github.com/heldersindique-prog/wazuh-siem
