# Dia 1 - 28 de agosto de 2026

## Turno: triagem de incidentes

### Contexto

Primeiro dia da rotina de simulacao de SOC Analyst. Ponto de partida: 3 incidentes pendentes no Microsoft Sentinel, gerados por uma regra de deteccao de brute-force RDP (`rdp-bruteforce-demo`) criada num projeto anterior ([azure-mini-soc](https://github.com/heldersindique-prog/azure-mini-soc)).

### Triagem

Fila inicial (via `az sentinel incident list`):

| Numero | Titulo | Severidade | Status |
|---|---|---|---|
| 1 | RDP Brute Force - Multiple Failed Logons | Medium | New |
| 2 | RDP Brute Force - Multiple Failed Logons | Medium | New |
| 3 | RDP Brute Force - Multiple Failed Logons | Medium | New |

Investigacao confirmou: os 3 incidentes correspondem a testes controlados, gerados propositadamente para validar a regra de deteccao (tentativas de login RDP com password incorreta contra a VM `vm-soc-demo`).

### Classificacao e fecho

Os 3 incidentes foram fechados via Azure CLI, classificados como `BenignPositive` / `SuspiciousButExpected` (ataque real e corretamente detetado, mas sem ameaca real ao ambiente, por ser um teste conhecido):

```bash
az sentinel incident update --resource-group rg-mini-soc --workspace-name law-mini-soc \
  --incident-id "<id>" \
  --title "RDP Brute Force - Multiple Failed Logons" \
  --severity "Medium" \
  --status "Closed" \
  --classification "BenignPositive" \
  --classification-reason "SuspiciousButExpected" \
  --classification-comment "Teste controlado de brute-force RDP realizado pelo proprio analista para validar deteccao da regra rdp-bruteforce-demo."
```

### Licoes tecnicas

- `az sentinel incident update` funciona como um PUT completo, nao um PATCH parcial: exige sempre reenviar `--title`, `--severity` e `--status` mesmo que so se queira mudar a classificacao.
- As combinacoes de `--classification` e `--classification-reason` sao fixas. `SuspiciousButExpected` so e valido com `BenignPositive`, nao com `TruePositive`.
- O Defender portal (security.microsoft.com) apresentou um bug de sincronizacao: incidentes corretamente fechados via API nao apareciam na lista mesmo com o filtro de status a incluir "Closed". Confirmado o estado real diretamente via `az sentinel incident list`, que e a fonte de verdade quando o portal parece inconsistente.

### Resultado do turno

Fila de incidentes limpa. 3 casos fechados e documentados, com comentario de auditoria em cada um.
