# Dia 1 - 28 de agosto de 2026

## Turno: triagem de incidentes

### Contexto

Primeiro dia da rotina de simulacao de SOC Analyst. Ponto de partida: 3 incidentes pendentes no Microsoft Sentinel, gerados por uma regra de deteccao de brute-force RDP (`rdp-bruteforce-demo`) criada num projeto anterior ([azure-mini-soc](https://github.com/heldersindique-prog/azure-mini-soc)).

### Triagem

Fila inicial (via `az sentinel incident list`):

| Numero | Titulo | Severidade | Status |
|---|---|---|---|
| 1 | RDP Brute Force - Multiple Failed Logons | Medium | New |
| 2 | RDP Brute Force - Multiple Failed Logons | Medium | New |
| 3 | RDP Brute Force - Multiple Failed Logons | Medium | New |

Investigacao confirmou: os 3 incidentes correspondem a testes controlados, gerados propositadamente para validar a regra de deteccao (tentativas de login RDP com password incorreta contra a VM `vm-soc-demo`).

### Classificacao e fecho

Os 3 incidentes foram fechados via Azure CLI, classificados como `BenignPositive` / `SuspiciousButExpected` (ataque real e corretamente detetado, mas sem ameaca real ao ambiente, por ser um teste conhecido):

```bash
az sentinel incident update --resource-group rg-mini-soc --workspace-name law-mini-soc \
  --incident-id "<id>" \
  --title "RDP Brute Force - Multiple Failed Logons" \
  --severity "Medium" \
  --status "Closed" \
  --classification "BenignPositive" \
  --classification-reason "SuspiciousButExpected" \
  --classification-comment "Teste controlado de brute-force RDP realizado pelo proprio analista para validar deteccao da regra rdp-bruteforce-demo."
```

### Licoes tecnicas

- `az sentinel incident update` funciona como um PUT completo, nao um PATCH parcial: exige sempre reenviar `--title`, `--severity` e `--status` mesmo que so se queira mudar a classificacao.
- As combinacoes de `--classification` e `--classification-reason` sao fixas. `SuspiciousButExpected` so e valido com `BenignPositive`, nao com `TruePositive`.
- O Defender portal (security.microsoft.com) apresentou um bug de sincronizacao: incidentes corretamente fechados via API nao apareciam na lista mesmo com o filtro de status a incluir "Closed". Confirmado o estado real diretamente via `az sentinel incident list`, que e a fonte de verdade quando o portal parece inconsistente.

### Resultado do turno

Fila de incidentes limpa. 3 casos fechados e documentados, com comentario de auditoria em cada um.

## Turno 2: construcao do honeypot T-Pot (Oracle Cloud)

### Contexto

Com a fila de incidentes do Sentinel limpa, iniciada a construcao de uma fonte continua de trafego de ataque real: um honeypot publico usando T-Pot, na Oracle Cloud Infrastructure (recursos Always Free).

### Progresso

- Conta OCI localizada e acesso recuperado (tenancy `heldersindique`, home region Spain Central/Madrid)
- Rede criada manualmente (VCN `vcn-honeypot`, Internet Gateway `ig-honeypot`, Route Table com rota `0.0.0.0/0`, Subnet publica `subnet-honeypot`)
- OCI CLI instalado e autenticado no servidor via API Signing Key
- Chave SSH dedicada gerada (`~/.ssh/tpot_honeypot`)

### Obstaculo: falta de capacidade Always Free (Ampere A1.Flex)

Tentativas de criar a instancia `VM.Standard.A1.Flex` (4 OCPU / 24GB) via portal falharam com `Out of capacity for shape VM.Standard.A1.Flex in availability domain AD-1`. E um problema amplamente documentado na comunidade: a shape Ampere A1 e muito popular no tier Always Free e a capacidade esgota-se com frequencia.

Como a home region (Madrid) so tem uma availability domain, nao havia outra AD para alternar.

**Solucao aplicada**: script de retry automatico (`retry-create-honeypot.sh`) via OCI CLI, a correr em background no servidor (`nohup ... &`), a tentar criar a instancia a cada 60 segundos ate a Oracle libertar capacidade. Log de progresso em `~/honeypot-retry.log`.

### Licoes tecnicas

- Distincao entre "Oracle Account" (identidade generica, MyLearn, foruns) e "Cloud Account/tenancy" (infraestrutura) - sao sistemas diferentes, e o email de boas-vindas de cada um e distinto. O nome do tenancy so aparece no email "Your Oracle Cloud Account is Fully Provisioned".
- Ao criar uma instancia end-to-end no wizard do portal, o toggle de IP publico pode ficar bloqueado mesmo com subnet publica selecionada - mais fiavel criar a rede (VCN, Internet Gateway, Route Table, Subnet) separadamente primeiro, e so depois selecionar essa rede ja existente ao criar a instancia.
- `oci setup config` (modo interativo) pode entrar em loop de erro ao definir a passphrase da chave privada; mais fiavel gerar a chave manualmente com `openssl genrsa` e escrever o ficheiro `~/.oci/config` diretamente.
- Erros `NotAuthenticated` logo a seguir a configurar uma API key nova podem ser apenas atraso de propagacao (1-2 minutos) do lado da Oracle, nao um erro de configuracao.

### Estado no fim do turno

Script de retry ativo em background (PID registado no servidor), a tentar criar a instancia `tpot-honeypot` automaticamente. Proximo turno: confirmar se a instancia foi criada, instalar o T-Pot, e ligar os logs ao Wazuh.
